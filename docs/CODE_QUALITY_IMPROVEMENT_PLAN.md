# خطة رفع جودة الكود في Utility ERP

## 1. الهدف

تهدف هذه الخطة إلى رفع جودة كود إضافات `utility_erp` تدريجياً بدون تعطيل التطوير الحالي، مع التركيز على:

1. تقليل الأخطاء في مسارات الفوترة والتحصيل والقراءات.
2. تثبيت قواعد واضحة لبنية الموديولات والاعتمادات.
3. تحسين الأمان والصلاحيات، خصوصاً مع بيانات العملاء والمدفوعات.
4. تجهيز المشروع لاحقاً لاختبارات آلية وعمليات نشر أكثر استقراراً.
5. جعل الكود أسهل في الصيانة والتوسع لموديولات `utility_core`, `utility_prepaid`, `utility_operations`, `utility_billing`, `utility_portal`, و`utility_inventory`.

## 2. نطاق الخطة

تشمل الخطة جميع إضافات Odoo داخل المستودع:

- `utility_core`: البيانات الأساسية، المشتركين، العدادات، التعرفة، الإعدادات، الصيغ.
- `utility_prepaid`: الدفع المسبق، التوكنات، POS، الورديات.
- `utility_operations`: أوامر الخدمة، التفتيش، المخالفات، الاستبدال، التسويات.
- `utility_billing`: الفوترة اللاحقة، القراءات، أوامر البيع، التحصيل، الغرامات، المجدولات.
- `utility_portal`: البوابة وواجهات API.
- `utility_inventory`: تكامل المخزون والعدادات، ويعامل كموديول تابع لاحقاً للطبقات الأساسية.

## 3. مبادئ الجودة المعتمدة

1. الالتزام بترتيب الاعتمادات: يبدأ أي تغيير مؤثر من `utility_core` ثم الموديولات التابعة حسب الحاجة.
2. عدم إعادة تقديم النماذج المحذوفة مثل `utility.bill`, `utility.collection`, و`utility.sale`، واستخدام بدائل Odoo القياسية الحالية.
3. فصل منطق الأعمال عن الواجهات قدر الإمكان، وعدم وضع قواعد حرجة داخل XML أو أزرار فقط.
4. جعل العمليات الدُفعية آمنة وقابلة لإعادة المحاولة، خصوصاً الفوترة، التذكيرات، الغرامات، ورفع القراءات.
5. اعتبار الماليات، الصلاحيات، وبيانات العملاء مناطق عالية الخطورة تحتاج مراجعة إضافية.
6. توثيق أي قرار معماري مؤثر في ملف Markdown داخل `docs/`.

## 4. المرحلة الأولى: جرد الجودة والمخاطر

### 4.1 جرد الموديولات والاعتمادات

المطلوب:

1. مراجعة ملفات `__manifest__.py` لكل موديول.
2. التأكد من عدم وجود اعتماد عكسي يكسر ترتيب الطبقات.
3. توثيق الاعتمادات الفعلية، خصوصاً:
   - اعتماد `utility_billing` على `utility_core` و`utility_prepaid`.
   - اعتماد `utility_inventory` على نماذج العدادات والعملاء.
   - اعتماد `utility_portal` على كل الموديولات التشغيلية.

معيار القبول:

- وجود جدول واضح يوضح كل موديول واعتماداته المباشرة.
- عدم وجود import أو مرجع XML من موديول منخفض إلى موديول أعلى.

### 4.2 جرد النماذج الحساسة

المطلوب:

1. تحديد النماذج التي تمس الماليات أو بيانات العملاء:
   - `sale.order` الموروث في `utility_billing`.
   - `account.payment` الموروث.
   - `pos.order` الموروث.
   - `utility.customer`.
   - `utility.reading`.
   - `utility.formula`.
2. تحديد الدوال الحرجة مثل:
   - `_calculate_amounts()`.
   - `_generate_token()`.
   - `cron_update_overdue_orders`.
   - `cron_calculate_late_penalties`.
   - دوال توليد الفواتير من القراءات.

معيار القبول:

- إنشاء قائمة مراجعة لكل نموذج حساس: الحقول المالية، الحالات، الصلاحيات، الدوال المجدولة، ونقاط التكامل.

## 5. المرحلة الثانية: تحسين بنية الكود

### 5.1 توحيد أسلوب النماذج

المطلوب:

1. ترتيب ملفات Python داخلياً بأسلوب ثابت:
   - imports.
   - تعريف `_name` أو `_inherit`.
   - الحقول.
   - القيود.
   - compute/onchange.
   - أزرار الإجراءات.
   - دوال cron.
   - الدوال المساعدة الخاصة.
2. تسمية دوال الأفعال بوضوح مثل `action_confirm_reading`, `action_generate_bill`, `action_requeue`.
3. نقل المنطق المتكرر إلى دوال داخلية صغيرة عند وجود تكرار فعلي.

معيار القبول:

- قراءة أي نموذج رئيسي لا تتطلب تتبع منطق مبعثر بين عدة أماكن بلا سبب.
- عدم وجود دوال طويلة جداً في مسارات حرجة بدون تقسيم منطقي.

### 5.2 ضبط حقول الحالات

المطلوب:

1. توثيق state machine لكل نموذج يستخدم `state` أو `bill_state`.
2. منع الانتقالات غير الصالحة من خلال دوال أفعال واضحة.
3. التأكد من أن `bill_state` في `sale.order` لا يختلط مع `sale.order.state`.
4. الحفاظ على دورة قراءة العداد الحالية:
   `draft -> under_review -> approved -> billed`.

معيار القبول:

- لكل حالة زر أو دالة انتقال واضحة.
- لا توجد writes مباشرة للحالة في أماكن متعددة بدون سبب واضح.

### 5.3 تحسين التعليقات والتوثيق داخل الكود

المطلوب:

1. إضافة تعليقات قصيرة فقط حول المنطق المعقد.
2. تجنب التعليقات التي تعيد وصف السطر نفسه.
3. توثيق الدوال الحرجة بـ docstring مختصر يوضح المدخلات والآثار الجانبية.

معيار القبول:

- الدوال المالية والمجدولة واضحة الغرض والآثار.
- لا توجد تعليقات كثيرة تخفي ضعف تصميم الدالة.

## 6. المرحلة الثالثة: الأمان والصلاحيات

### 6.1 مراجعة مجموعات الصلاحيات

المطلوب:

1. مراجعة `utility_core/security/utility_security.xml`.
2. معالجة مشكلة أن كل المجموعات imply `group_utility_admin` أو توثيقها كدين فني واضح قبل أي تعديل.
3. تحديد أدوار فعلية منفصلة:
   - مدير النظام.
   - مدير الفوترة.
   - المحصل.
   - القارئ.
   - الفني.
   - المشرف.
   - المدقق.
   - مستخدم البوابة/API.

معيار القبول:

- لا يحصل المستخدم العادي على صلاحيات مدير بشكل غير مباشر.
- الأزرار الحساسة لا تعتمد على إخفاء الواجهة فقط، بل على صلاحيات server-side أيضاً.

### 6.2 مراجعة `sudo()`

المطلوب:

1. حصر كل استخدامات `sudo()`.
2. تصنيف كل استخدام:
   - ضروري لقراءة إعدادات النظام.
   - ضروري لعملية تقنية.
   - خطر أو غير مبرر.
3. إزالة أو تضييق أي `sudo()` غير مبرر، خصوصاً في بيانات العملاء والمدفوعات والمرفقات.

معيار القبول:

- كل `sudo()` في الكود له سبب واضح.
- لا توجد عمليات كتابة مالية بـ `sudo()` إلا إذا كانت مبررة ومحمية.

### 6.3 مراجعة `safe_eval`

المطلوب:

1. مراجعة `utility.formula` وأي استخدام آخر لـ `safe_eval`.
2. تحديد المتغيرات المسموحة بوضوح:
   `consumption`, `previous_reading`, `current_reading`, `tariff`, `account`, `category`, `line`, `result`, `name`.
3. منع الوصول غير الضروري إلى `env`, `cr`, أو نماذج Odoo من داخل الصيغ.
4. إضافة سجل أخطاء واضح عند فشل تنفيذ الصيغة بدون كشف تفاصيل حساسة للمستخدم النهائي.

معيار القبول:

- الصيغ الديناميكية لا تستطيع تعديل سجلات خارج نطاق الحساب المطلوب.
- فشل الصيغة لا يؤدي إلى فشل دفعة فوترة كاملة.

## 7. المرحلة الرابعة: جودة مسارات الأعمال

### 7.1 الفوترة عبر `sale.order`

المطلوب:

1. مراجعة `utility_billing/models/utility_sale_order.py`.
2. التأكد من أن `_calculate_amounts()`:
   - لا يكرر بنود الفاتورة عند إعادة الحساب.
   - يستخدم `order_line` فقط.
   - يحترم قالب العقد والتعرفة والصيغ.
   - يعالج الأخطاء بطريقة قابلة للفهم.
3. التأكد من أن الحقول المالية المحسوبة لا تتعارض مع حقول Odoo القياسية مثل `amount_total`.

معيار القبول:

- إعادة حساب الفاتورة عملية idempotent قدر الإمكان.
- لا توجد فروقات غير مفسرة بين `amount_total`, `balance_due`, و`amount_paid`.

### 7.2 القراءات والفوترة الدُفعية

المطلوب:

1. مراجعة دورة حياة `utility.reading`.
2. التأكد من عدم فوترة نفس القراءة أكثر من مرة.
3. اعتماد معالجة دفعية تستخدم batch size من `ir.config_parameter`.
4. تسجيل خطأ كل قراءة فاشلة بدون إيقاف كامل الدفعة.

معيار القبول:

- يمكن إعادة محاولة القراءة الفاشلة بعد تصحيح بياناتها.
- يوجد أثر واضح يربط القراءة بالفاتورة الناتجة.

### 7.3 المدفوعات والتحصيل

المطلوب:

1. مراجعة ربط `account.payment` مع `utility_sale_order_id`.
2. منع تطبيق دفعة على فاتورة خاطئة أو ملغاة.
3. ضبط حالات الدفع الجزئي والكامل.
4. التحقق من توافق الورديات مع المدفوعات الفعلية.

معيار القبول:

- لا يمكن أن يصبح `bill_state = paid` مع وجود رصيد مستحق موجب.
- الورديات تعرض فروقات واضحة بين المتوقع والفعلي.

### 7.4 الدفع المسبق وPOS

المطلوب:

1. مراجعة توليد STS token من `pos.order`.
2. التأكد من عدم توليد التوكن مرتين لنفس الطلب.
3. ربط التوكن، الحركة، والطلب بشكل قابل للتتبع.
4. مراجعة دوال العكس `reversal` والتسويات.

معيار القبول:

- كل توكن له مصدر واحد واضح.
- إلغاء أو عكس عملية لا يترك أرصدة أو سجلات متناقضة.

## 8. المرحلة الخامسة: الاعتمادية والأداء

### 8.1 تحسين الدوال المجدولة

المطلوب:

1. حصر جميع دوال cron.
2. إضافة حدود batch size لأي دالة تعالج سجلات كثيرة.
3. استخدام savepoints أو معالجة سجلية آمنة في العمليات الكبيرة.
4. تسجيل عدد السجلات الناجحة والفاشلة.

معيار القبول:

- فشل سجل واحد لا يوقف معالجة آلاف السجلات.
- يمكن معرفة نتيجة آخر تشغيل من اللوج أو من حقل متابعة.

### 8.2 تحسين البحث والحسابات

المطلوب:

1. مراجعة الدوال التي تستدعي `search` داخل loops.
2. استخدام prefetch وmapped/read_group عند الحاجة.
3. مراجعة حقول `store=True` للحقول المحسوبة الثقيلة.
4. إضافة فهارس SQL عند وجود بحث متكرر على حقول كبيرة، بعد قياس الحاجة.

معيار القبول:

- لا توجد عمليات بحث متكررة واضحة داخل loops حرجة.
- الشاشات الرئيسية للقراءات والفواتير لا تعتمد على compute ثقيل غير مخزن.

### 8.3 المرفقات والصور

المطلوب:

1. مراجعة تخصيص `ir.attachment`.
2. التأكد من أن مسارات التخزين آمنة ولا تقبل مسارات خارجية غير متوقعة.
3. ضبط صلاحيات صور العدادات والمرفقات المالية.

معيار القبول:

- لا يمكن لمستخدم غير مصرح له الوصول إلى صور أو مرفقات عميل آخر.
- لا توجد كتابة ملفات خارج مسار التخزين المتوقع.

## 9. المرحلة السادسة: الاختبارات والتحقق

لا توجد بنية اختبارات حالياً، لذلك لا يتم تشغيل `odoo-test` قبل إنشاء الاختبارات فعلياً.

### 9.1 إنشاء أساس الاختبارات

المطلوب:

1. إنشاء اختبارات صغيرة لكل موديول تدريجياً.
2. البدء بـ `utility_core` لأنه الأساس.
3. استخدام بيانات اختبار محدودة وواضحة.
4. عدم الاعتماد على بيانات demo في اختبارات منطق الأعمال.

أولوية الاختبارات:

1. إنشاء عميل وحساب وعداد وتعرفة.
2. إنشاء قراءة واعتمادها.
3. توليد فاتورة `sale.order` من القراءة.
4. إعادة حساب فاتورة وعدم تكرار البنود.
5. تسجيل دفعة وربطها بالفاتورة.
6. توليد توكن prepaid مرة واحدة.
7. تنفيذ صيغة ديناميكية صحيحة وفشل صيغة خاطئة بأمان.

معيار القبول:

- وجود أول مجموعة اختبارات تغطي المسار الأساسي من قراءة إلى فاتورة.
- الاختبارات لا تحتاج بيانات إنتاجية.

### 9.2 اختبارات XML والصلاحيات

المطلوب:

1. اختبار تحميل views وmenus بدون أخطاء.
2. اختبار أن المستخدمين حسب الأدوار يرون ويعدلون فقط ما يسمح لهم.
3. اختبار قيود access CSV على النماذج الجديدة.

معيار القبول:

- لا توجد views تشير إلى حقول أو groups غير موجودة.
- صلاحيات المستخدمين متوافقة مع workflow الفعلي.

## 10. المرحلة السابعة: أدوات الجودة

### 10.1 الحد الأدنى المقترح

المطلوب إضافته لاحقاً:

1. ملف إعدادات formatting/linting مناسب لـ Python.
2. أمر موحد لتشغيل فحص بسيط على ملفات Python وXML.
3. توثيق أوامر التطوير في `README.md`.
4. قائمة فحص Pull Request داخل `docs/` أو قالب PR عند وجود منصة Git.

ملاحظة:

- يجب عدم إضافة أدوات ثقيلة تعطل الفريق قبل وجود اختبارات وبنية تشغيل واضحة.
- الأفضل البدء بفحوصات بسيطة وغير خلافية.

### 10.2 قائمة فحص قبل الدمج

أي تعديل مؤثر يجب أن يجيب على الأسئلة التالية:

1. هل غيّر التعديل نموذج بيانات أو حقل مالي؟
2. هل يحتاج migration أو default values؟
3. هل يؤثر على ترتيب تثبيت الموديولات؟
4. هل يحتاج صلاحيات access أو groups جديدة؟
5. هل يؤثر على `sale.order`, `account.payment`, أو `pos.order`؟
6. هل يعمل بأمان على آلاف السجلات؟
7. هل يحتاج اختباراً آلياً أو سيناريو تحقق يدوي موثق؟

## 12. خطة تنفيذ مقترحة على أربع دفعات

### الدفعة 1: أسبوع الجودة الأساسي

1. جرد الاعتمادات والنماذج الحساسة.
2. حصر `sudo()` و`safe_eval`.
3. مراجعة صلاحيات groups وaccess CSV.
4. فتح قائمة issues داخلية أو ملف متابعة للديون الفنية.

الناتج:

- قائمة مخاطر واضحة.
- قرارات أولية حول الصلاحيات والصيغ.

### الدفعة 2: تثبيت الفوترة والتحصيل

1. مراجعة `_calculate_amounts()`.
2. تثبيت عدم تكرار بنود الفاتورة.
3. مراجعة انتقالات `bill_state`.
4. مراجعة ربط `account.payment`.

الناتج:

- مسار فوترة أكثر استقراراً.
- حالات دفع أوضح.

### الدفعة 3: الاعتمادية والأداء

1. مراجعة كل cron.
2. تطبيق batch size قابل للإعداد.
3. إضافة logging واضح للنجاح والفشل.
4. تحسين searches داخل loops.

الناتج:

- عمليات خلفية أقل عرضة للفشل الكامل.
- قابلية أفضل للتشغيل على بيانات كبيرة.

### الدفعة 4: الاختبارات والتوثيق

1. إنشاء اختبارات أولية في `utility_core` و`utility_billing`.
2. توثيق أوامر التحقق المتاحة.
3. إضافة checklist للمراجعة.
4. تحديث README بخطوات التثبيت وترتيب الموديولات.

الناتج:

- أساس اختبار قابل للتوسع.
- طريقة عمل أوضح للمطورين.

## 13. مؤشرات قياس الجودة

يتم قياس التحسن عبر المؤشرات التالية:

1. عدد استخدامات `sudo()` غير المبررة يساوي صفر.
2. كل دالة cron رئيسية لها batch size ومعالجة أخطاء.
3. لا توجد فوترة مكررة لنفس القراءة في السيناريوهات الأساسية.
4. توجد اختبارات تغطي مسار قراءة -> فاتورة -> دفع.
5. كل نموذج مالي أو تشغيلي حساس لديه access rules واضحة.
6. كل تغيير كبير في نموذج البيانات موثق.
7. لا توجد views مكسورة أو references لموديلات محذوفة.

## 15. تعريف الإنجاز

تعتبر خطة رفع الجودة منجزة في مرحلتها الأولى عند تحقق التالي:

1. توثيق الاعتمادات والمخاطر.
2. مراجعة الصلاحيات و`sudo()` و`safe_eval`.
3. تثبيت مسار الفوترة الأساسي وعدم تكرار البنود.
4. تحسين دوال cron الحرجة لمعالجة الفشل الجزئي.
5. إضافة أول اختبارات آلية لمسار القراءة إلى الفاتورة.
6. تحديث التوثيق الأساسي للمطورين.
